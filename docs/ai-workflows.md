# AI workflows

The app-level AI operations, the layer that owns each one, and how caching and
tracing behave. For provider primitives (which SDK, which model) read
[`src/server/aiService.ts`](../src/server/aiService.ts),
[`src/server/images/`](../src/server/images/), and
[`src/server/tts/`](../src/server/tts/).

## The shape of every call

The browser never talks to a provider. [`src/ai.ts`](../src/ai.ts) is the single
client: it POSTs to `/api/...`, and the Node server holds the keys, makes the
call, writes any generated file, and caches what can be cached.

```text
feature code → src/ai.ts → /api/... → src/server/* → provider
```

Text calls go through one pair of primitives (`completeAi`, `streamAi`) that
dispatch on the model id — `claude-*` to Anthropic, `gemini-*` to Google,
everything else to OpenAI. Callers pick an operation, not a provider.

## The operations

| Operation | Owner | Notes |
| --- | --- | --- |
| **Story planning / generation** (reading) | [`src/server/openingsStore.ts`](../src/server/openingsStore.ts) when queued; [`src/story_session/`](../src/story_session/) when generated on demand. Prompt and parser in [`src/story.ts`](../src/story.ts). | One call produces a whole six-part story plus its metadata. Sent the learner profile, preferences, story memory, and a randomized diversity recipe. Validated as complete; repaired once, then rejected. |
| **Story opening** (typing) | [`src/server/openingsStore.ts`](../src/server/openingsStore.ts), or `startStory` in [`src/ai.ts`](../src/ai.ts) as fallback. | Includes a title and a second-person intro. |
| **Story continuation** (typing) | [`src/story_session/`](../src/story_session/), streamed. | The only streaming operation. Reading stories never use it. |
| **Story memory (rolling summary)** | [`src/story_memory/`](../src/story_memory/) | Compacts a long typing history so the prompt stays bounded. Fires only once the unsummarized buffer crosses its threshold — not on every turn. |
| **Reading narration** | The media owner in [`src/story_session/`](../src/story_session/); synthesized by [`src/server/storyAudioStore.ts`](../src/server/storyAudioStore.ts). | One request per section, deduplicated per story/section/voice/text. |
| **Word pronunciation** | [`src/server/wordAudioStore.ts`](../src/server/wordAudioStore.ts) | One file per word, reused across every story. Always Gemini TTS. |
| **Lesson audio** | [`src/server/lessonAudioStore.ts`](../src/server/lessonAudioStore.ts) | One file per lesson + text. Always OpenAI TTS. |
| **Background-image generation** | Requested by [`src/story_session/`](../src/story_session/), generated by [`src/server/openingsStore.ts`](../src/server/openingsStore.ts) via [`src/server/images/`](../src/server/images/). | Reading passes a hidden visual-continuity description so the character and place stay stable across sections. |
| **Translation** | [`src/server/aiEndpointHandlers.ts`](../src/server/aiEndpointHandlers.ts) over [`src/server/translationCacheStore.ts`](../src/server/translationCacheStore.ts). | Batched: only words missing from the cache are sent. |
| **Recap generation** | [`src/story_session/`](../src/story_session/), with the spec and parser in [`src/storyRecap.ts`](../src/storyRecap.ts). | Built from the finished prose, the per-part language focuses, the word translations, and the learner profile. |
| **Lesson generation** | [`src/lessons/lessonGeneration.ts`](../src/lessons/lessonGeneration.ts), invoked through [`src/ai.ts`](../src/ai.ts). | The model authors body bricks only; exercises are derived from the parsed body in code. |
| **Learner-profile refinement** | [`src/server/learnerProfileService.ts`](../src/server/learnerProfileService.ts) | Three entry points: tutor-chat transcript, finished story (summary + word lookups + feedback), and recap results. Rewrites the whole one-page handout; never appends. |
| **Learner-preferences refinement** | [`src/server/learnerProfileService.ts`](../src/server/learnerProfileService.ts) | Refined from the tutor chat, alongside the profile. |
| **Story-memory refinement** | [`src/server/learnerProfileService.ts`](../src/server/learnerProfileService.ts) | Refined when a reading story finishes. Extracts motifs, objects, and settings, and writes "avoid next" guidance for the following story. |
| **Esperanto tutor chat** | [`src/ai.ts`](../src/ai.ts) (`askEsperantoTutor`), rendered by [`src/exercise_screen/`](../src/exercise_screen/). | Story context is passed in; the transcript later feeds profile and preference refinement. |

Refinement is fire-and-forget: it must never block or break the learner's flow,
so failures leave the handout exactly as it was.

All learner-supplied text (profile, preferences, memory, chat transcripts) is
passed to the model as **untrusted data**, with explicit instructions not to
treat it as commands. Keep that framing when adding a prompt that reads learner
content.

## Caching, and why it matters for traces

Several operations are cached, and a cache hit **must not reach a provider**:

- **Translations** — [`translation-cache.json`](./local-data.md) is consulted
  first; only misses are sent.
- **Word audio** — one file per word; a hit returns the file's URL.
- **Lesson audio** — one file per lesson and text.
- **Section narration** — an existing section audio file for the same story,
  section, voice, and text is returned as-is.
- **In-flight requests** — the reading media owner and the background-image store
  both join an identical request already running instead of starting a second
  one. Images are billed per call and are not content-addressed, so this is the
  only thing standing between a double-request and a double charge.

Tracing wraps the **provider call**, not the operation. A cache hit therefore
produces no trace record at all. That is the intended behavior, and it is what
makes the trace log usable as a cost and latency ledger: every line in it is a
call that was actually billed.

If you add a cache, put it *outside* `traceAiCall`. If you find yourself wanting
a "cache hit" record in the AI trace, that belongs in a different log.

## The trace log

Enabled with `AI_CALL_LOG=1` (or `AI_TRACE=1`) in the server's environment;
disabled entirely otherwise. Records are appended as newline-delimited JSON to
`logs/ai-calls.ndjson`, one per provider call, each with a timestamp, the
request id and endpoint that caused it, the kind, provider, model, whether it
streamed, duration, success, and payload summaries. Failures record the error.

The traced kinds are `text.complete`, `text.stream`, `text.translation`,
`image.generate`, and `audio.speech`.

**Reset versus append.** The log file is truncated once per server process, the
first time a record is written. Set `AI_CALL_LOG_APPEND=1` to skip the truncation
and keep appending across restarts.

**Preview versus full payloads.** By default each input and output is summarized
— its size, and a 500-character preview. With `AI_CALL_LOG_PAYLOAD=full`, the
complete request and response payloads are stored instead. That means whole
prompts, whole stories, the learner's profile, and the learner's chat messages
land in the file verbatim. `logs/` is git-ignored; do not paste full-payload
records into issues, docs, or commits.

Two commands read the log (both defined in
[`package.json`](../package.json)):

```bash
npm run ai-log:summary  # one line per call: time, status, duration, model, kind, endpoint,
                        # then totals, failure count, average, and the slowest call
npm run ai-log:pretty   # writes .artifacts/ai-calls.pretty.json — the same records,
                        # indented, for reading in an editor
```

Both read `logs/ai-calls.ndjson` and fail loudly if a line is not valid JSON.
Neither one calls a provider.
