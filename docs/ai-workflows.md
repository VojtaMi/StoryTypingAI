# AI workflows

The app-level AI operations, the layer that owns each one, and how caching and
tracing behave. For provider primitives (which SDK, which model) read
[`src/server/aiService.ts`](../src/server/aiService.ts),
[`src/server/images/`](../src/server/images/), and
[`src/server/tts/`](../src/server/tts/).

## The shape of every call

The browser never talks to a provider. [`src/ai.ts`](../src/ai.ts) is the single
client: it POSTs to `/api/...`, and the Node server holds the keys, makes the
call, writes any generated file, and caches what can be cached.

```text
feature code → src/ai.ts → /api/... → src/server/* → provider
```

Text calls go through shared completion primitives that dispatch on the model
id — `claude-*` to Anthropic, `gemini-*` to Google, everything else to OpenAI.
Generic text and structured JSON preserve the provider output. Typing-story
boundaries normalize curly quotes, dashes, ellipses, and lightweight emphasis
into keyboard-friendly text. Callers pick an operation and output contract, not
a provider.

## The operations

| Operation | Owner | Notes |
| --- | --- | --- |
| **Story planning / generation** (reading) | [`src/server/openingsStore.ts`](../src/server/openingsStore.ts) queues it; staged contracts live in [`src/reading_story/`](../src/reading_story/) and orchestration/final validation in [`src/story.ts`](../src/story.ts). | Luna Low drafts and reviews one compact English plot. The selected story model expands the reviewed plot and pedagogical brief into uninterrupted Esperanto prose. Luna None chooses the natural count and semantic sentence boundaries for 2-8 similarly sized event-based parts, without rewriting. Luna then produces the shared visual core and exactly `ceil(parts / 2)` scene instructions. Plot preparation receives an explicit or handoff subject when one exists, otherwise it chooses freely from the preferences and narrative scale. It never receives language calibration, focus, raw learner history, or the Esperanto genre label as a creative subject. |
| **Story opening** (typing) | [`src/server/openingsStore.ts`](../src/server/openingsStore.ts), or `startStory` in [`src/ai.ts`](../src/ai.ts) as fallback. | Includes a title and a second-person intro. |
| **Story continuation** (typing) | [`src/story_session/`](../src/story_session/), streamed. | The only streaming operation. Reading stories never use it. |
| **Story memory (rolling summary)** | [`src/story_memory/`](../src/story_memory/) | Compacts a long typing history so the prompt stays bounded. Fires only once the unsummarized buffer crosses its threshold — not on every turn. |
| **Reading narration** | The media owner in [`src/story_session/`](../src/story_session/); synthesized by [`src/server/storyAudioStore.ts`](../src/server/storyAudioStore.ts). | One request per section, deduplicated per story/section/voice/text. |
| **Word pronunciation** | [`src/server/wordAudioStore.ts`](../src/server/wordAudioStore.ts) | One file per word, reused across every story. Always Gemini TTS. |
| **Lesson audio** | [`src/server/lessonAudioStore.ts`](../src/server/lessonAudioStore.ts) | One file per lesson + text. Always OpenAI TTS. |
| **Background-image generation** | Requested by [`src/story_session/`](../src/story_session/), generated by [`src/server/openingsStore.ts`](../src/server/openingsStore.ts) via [`src/server/images/`](../src/server/images/). | Reading passes a hidden visual-continuity description so the character and place stay stable across sections. |
| **Translation** | [`src/server/aiEndpointHandlers.ts`](../src/server/aiEndpointHandlers.ts) over [`src/server/translationCacheStore.ts`](../src/server/translationCacheStore.ts). | Uses the default Luna model at `none` reasoning. Prepared reading stories warm the cache with all unique story words in one batch, excluding declared character names. The visible-section lookup remains a fallback; only words missing from the cache are sent. Ambiguous words may retain concise slash-separated alternatives. |
| **Recap generation** | [`src/story_session/`](../src/story_session/), with the spec and parser in [`src/storyRecap.ts`](../src/storyRecap.ts). | Built only from the finished prose, its stated language focus, and available word translations. |
| **Lesson generation** | [`src/lessons/lessonGeneration.ts`](../src/lessons/lessonGeneration.ts), invoked through [`src/ai.ts`](../src/ai.ts). | The model authors body bricks only; exercises are derived from the parsed body in code. |
| **Next-story brief** | [`src/server/nextStoryBriefService.ts`](../src/server/nextStoryBriefService.ts) | Finalization distills the completed prose, recap, story-scoped lookups, learner questions, difficulty, and practice request into a broad theme suggestion, an absolute `minimal` or `simple` narrative scale, and one language plan. Calibration snippets may quote or lightly paraphrase the completed story, but must remain representative of its language difficulty. |
| **Learner-profile refinement** | [`src/server/learnerProfileService.ts`](../src/server/learnerProfileService.ts) | Standalone tutor chat may maintain the bounded language profile used by legacy generated lessons. It cannot mutate explicit story preferences or reading handoffs. |
| **Esperanto tutor chat** | [`src/ai.ts`](../src/ai.ts) (`askEsperantoTutor`), rendered by [`src/exercise_screen/`](../src/exercise_screen/). | Story context is passed in. Outside a reading story, the transcript may refine only the legacy language profile. Inside a reading story, the learner's own questions are buffered as evidence for the next-story brief. |

Tutor-profile refinement is fire-and-forget: failures leave
`learner/state.json` exactly as it was. Explicit preferences are edited only in
Settings.

### The story-finish evidence manager

When a reading story ends, its evidence is distilled through a per-story record,
`stories/<id>/finish-evidence.json`, owned by
[`src/server/storyFinishEvidenceStore.ts`](../src/server/storyFinishEvidenceStore.ts).
It exists so finalization is **idempotent** and late feedback can never leak into
the next story:

- **Finalization** (`finalize-story`) runs when the learner completes the recap and
  submits feedback, or leaves the finished story without custom feedback. It sends
  story summary, all Esperanto parts, recap results, difficulty/practice
  feedback, buffered learner questions, and story-scoped word evidence together.
  The server produces one `NextStoryBrief` and stamps `finalizedAt`; repeating
  the trigger is a no-op.
- **Word lookups are story-scoped.** A lookup made while reading is tagged with its
  `storyId` and folded only by that story's finalization. Unscoped menu/tutor
  lookups are not reading-story evidence and never enter the brief.
- Evidence arriving after finalization is ignored. The successor is already
  bound to the stored handoff, so reopened stories cannot change it.
- Recap results are stored in the save until finalization, so abandoning the story
  before the recap is complete does not create a partial handoff.

The brief and `finalizedAt` are written together in the finish record. A failed
provider call leaves the record unfinalized so preparation can retry.

All learner-supplied text is passed as **untrusted data**, with explicit
instructions not to treat it as commands. Story generation receives validated,
bounded JSON—not raw finalization evidence or free-form Markdown handouts.

## Caching, and why it matters for traces

Several operations are cached, and a cache hit **must not reach a provider**:

- **Translations** — [`translation-cache.json`](./local-data.md) is consulted
  first; only misses are sent.
- **Word audio** — one file per word; a hit returns the file's URL.
- **Lesson audio** — one file per lesson and text.
- **Section narration** — an existing section audio file for the same story,
  section, voice, and text is returned as-is.
- **In-flight requests** — the reading media owner and the background-image store
  both join an identical request already running instead of starting a second
  one. Images are billed per call and are not content-addressed, so this is the
  only thing standing between a double-request and a double charge.

Tracing wraps the **provider call**, not the operation. A cache hit therefore
produces no trace record at all. That is the intended behavior, and it is what
makes the trace log usable as a cost and latency ledger: every line in it is a
call that was actually billed.

If you add a cache, put it *outside* `traceAiCall`. If you find yourself wanting
a "cache hit" record in the AI trace, that belongs in a different log.

## The trace log

Enabled with `AI_CALL_LOG=1` (or `AI_TRACE=1`) in the server's environment;
disabled entirely otherwise. Records are appended as newline-delimited JSON to
`logs/ai-calls.ndjson`, one per provider call, each with a timestamp, the
request id and endpoint that caused it, the kind, provider, model, whether it
streamed, duration, success, and payload summaries. Failures record the error.

The traced kinds are `text.complete`, `text.stream`, `text.translation`,
`image.generate`, and `audio.speech`.

**Reset versus append.** The log file is truncated once per server process, the
first time a record is written. Set `AI_CALL_LOG_APPEND=1` to skip the truncation
and keep appending across restarts.

**Preview versus full payloads.** By default each input and output is summarized
— its size, and a 500-character preview. With `AI_CALL_LOG_PAYLOAD=full`, the
complete request and response payloads are stored instead. That means whole
prompts, whole stories, the learner's profile, and the learner's chat messages
land in the file verbatim. `logs/` is git-ignored; do not paste full-payload
records into issues, docs, or commits.

Two commands read the log (both defined in
[`package.json`](../package.json)):

```bash
npm run ai-log:summary  # one line per call: time, status, duration, model, kind, endpoint,
                        # then totals, failure count, average, and the slowest call
npm run ai-log:pretty   # writes .artifacts/ai-calls.pretty.json — the same records,
                        # indented, for reading in an editor
```

Both read `logs/ai-calls.ndjson` and fail loudly if a line is not valid JSON.
Pass an archived trace as a second argument to compare a pipeline run, for
example `npm run ai-log:summary -- logs/archive/ai-calls-13.ndjson`. Neither
command calls a provider.

The text-only story-chain CLI can write a separate full-payload trace with
`--ai-log <path>`. Each call is labeled with its chain index and whether it
belongs to story generation or the next-story handoff. Because full traces can
contain learner state and story evidence, keep the output under a git-ignored
location such as `.artifacts/`.

For preference and progression experiments, pass `--scenario <path>`. A
scenario is an explicit timeline: `beforeStory` changes take effect before that
step is generated, while `afterStory` becomes evidence for its handoff. Omitted
preferences carry forward. For example:

```json
{
  "steps": [
    { "label": "baseline", "afterStory": { "difficulty": "tooEasy" } },
    {
      "label": "adventure preference",
      "beforeStory": {
        "preferences": {
          "prefer": ["engaging adventurous stories"],
          "avoid": ["school and household routines"]
        },
        "theme": "A cave expedition"
      },
      "afterStory": { "difficulty": "right" }
    }
  ]
}
```
